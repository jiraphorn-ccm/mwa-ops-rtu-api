rtu.cm_reports

23 columns · 1 PK · 5 FK

ไม่มีคอลัมน์ status สำหรับ CM ที่มี work_order — work_orders.status คือ single source of truth CHECK ck_cm_reports_origin: work_order_id IS NOT NULL OR pm_report_id IS NOT NULL (ต้องมีต้นทางอย่างน้อย 1 อย่าง) 3 ต้นทางของ CM report (แก้ตาม System Design "แจ้งซ่อม" flow, ไม่ใช่ 1 CM = 1 work_order เสมอ): 1. STANDALONE — work_order_id NOT NULL, pm_report_id NULL — Operator แจ้งปัญหาตรง (ไม่ผ่าน PM) 2. PM_ONSITE_FIX — work_order_id NULL, pm_report_id NOT NULL — กด "Report a Repair" ระหว่าง PM แล้วซ่อมจบในตัว "แนบเป็นส่วนหนึ่งของใบงาน PM (สร้าง CM Sub-record, Status = Completed ทันที)" — ไม่ต้องเปิด work_orders แถวใหม่ 3. PM_ESCALATED — work_order_id NOT NULL, pm_report_id NOT NULL — กด "Report an issue" ระหว่าง PM (ซ่อมไม่ได้) "Submit เป็น CM Work Order เต็มรูปแบบ (Status = Pending แยกเป็นใบงานของตัวเอง รอ CM Approval ทีหลัง)" origin คำนวณจาก (work_order_id, pm_report_id) ไม่ต้องเก็บเป็น column แยก สถานะ CM: STANDALONE/PM_ESCALATED (มี work_order_id) → ดูที่ work_orders.status ตามปกติ PM_ONSITE_FIX (work_order_id NULL) → ไม่มี column status เพราะไม่มี state อื่นให้เป็น — record นี้จะถูกสร้าง ก็ต่อเมื่อซ่อมสำเร็จแล้วเท่านั้น (ตามเอกสาร "สร้าง CM Sub-record, Status = Completed ทันที") ถือว่า COMPLETED โดยนัยเสมอ ไม่ต้อง query ที่ไหนเพิ่ม
